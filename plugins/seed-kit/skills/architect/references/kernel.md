# 架构知识内核

架构师审计的专业底座。每条按三段式使用：**意图**（它回答什么问题）、**代价**（它引入什么成本）、**反判据**（什么时候不该用它）。模式是词汇不是规定——引用名字是为了让取舍可讨论，不是为了套用；判定一个结构好不好，先过下面的判断基准，再谈模式。

## 判断基准（先于一切模式）

- **单一定义点**：每个实体、操作、状态只有一处权威定义。出现第二处即形态退化——重复的两份会各自漂移，测试往往只盖住其中一份。
- **依赖方向**：依赖指向稳定方，越稳定的越该是抽象（接口），越易变的越该是实现（SDP/SAP）。底层 import 高层、被依赖方知道所有调用方，都是方向腐化。
- **认知负荷边界**：一个模块要装得进一份工作记忆——对人是团队认知负荷（Team Topologies：一个团队最多管一个复杂域），对 agent 是一个干净 context window。装不下说明它是两个模块。边界即沟通结构（Conway）：沟通路径长的地方，边界迟早被绕过。
- **isolation 测试**：不看 internals 能否理解一个单元？改 internals 会不会破坏消费者？两个都过才是边界，否则边界没切对。
- **one-way door vs two-way door**：数据格式、对外契约、目录归属、状态语义是不可逆的贵决定，值得前置拍板；其余先走通，错了再改。
- **抽象时机**：第二个用例出现前不建抽象。抽象的正确性由"至少两个不同的真实消费者"证明，不是由"将来可能"证明。
- **change amplification**：一个好改动应该落在一处；同一个改动要动多处 = 放置错误或边界切错（对应 Fowler 的 Shotgun Surgery，但从源头防止而不是事后重构）。

## 对象与模块模式（高频精选）

| 模式 | 意图 | 代价 | 反判据 |
|---|---|---|---|
| 策略 | 运行时切换一族算法/渠道 | 一层间接 + 注册面 | 只有一个实现；分支能用判别字段穷举 |
| 工厂 | 构造复杂或带隐藏依赖的对象 | 与类型推断抢地盘 | 构造就是 `new` 一行；判别联合 + switch 更直 |
| 适配器 | 两端已定、中间翻译 | 翻译层自身要维护 | 一端本来就是自己写的——先改它 |
| 观察者 / 事件 | 生产者不该知道消费者 | 时序与生命周期难追踪 | 只有固定两个参与者；直接调用就够 |
| 装饰器 | 叠加正交能力（日志/重试/限流） | 层叠后调试变深 | 能力不正交；一个参数能表达 |
| 组合优先于继承 | 复用行为不绑类型层级 | 委托样板代码 | 继承只留给真正的 is-a 且层级稳定 |
| 状态机 | 显式枚举状态与合法迁移 | 迁移表要维护 | 状态 ≤2 且明确不会长 |
| 外观 | 给复杂子系统一个窄入口 | 面后面藏了真实边界 | 只包了一个对象——那是 Middle Man |

## 数据与状态模式

- **Repository**：隔离持久化细节，让领域层可测。代价：一层映射。反判据：只有一种存储且明确不会换——直接用。
- **事务脚本 vs 领域模型**：流程短平快用事务脚本；多实体联动、规则反复变才上领域模型。多数项目死于过早领域建模，不是没有模型。
- **聚合边界（DDD）**：聚合划的是一致性边界，不是分类学。跨聚合走事件与最终一致，不追求塞进一个事务。
- **事件溯源 / CQRS**：写模型与读模型分离的极端形态。审计追溯、时间旅行是刚需才用；否则是一笔复杂度贷款。
- **状态单点**：一份可变状态只有一个 owner（store / actor / 单写者）；其他地方派生，不复制。UI 状态尤其如此——派生即同步问题。

## 架构风格

- **分层**：依赖单向穿越层。代价：一个用户行为改一动全栈——所以交付按垂直切片切，每片穿所有层。
- **六边形 / 端口适配器**：领域在中心，IO 全是端口。"换供应商"（支付渠道、模型提供商、存储）诉求的正解；端口面就是未来的交换成本。
- **插件化 / seam**：一个能力 = 定义 + 实现 + 消费三角色，完整才成立；没有特权核心，新行为只能落进既有 seam——架构由拓扑强制，不靠自觉。
- **管道与过滤器**：流式数据加工，每级可测可换。反判据：中间产物没有第二个消费者——那是隐式耦合，不是复用。
- **事件驱动**：解耦生产与消费。代价：全局行为不可读，要拼事件流才能理解一个流程。确定性流程别用它。
- **ECS**（游戏 / 仿真）：数据与行为彻底分离，实体只是组件袋。海量同类实体 + 行为按系统迭代时优于 OOP 建模。
- **单调内核 + 外壳**：核心小而稳定，变化全部推到边缘（扩展点 / 配置）。插件体系、编辑器、解释器皆此形态。
- **绞杀者模式**：新旧并行、流量逐步迁移、最后拆除——大迁移不 Big Bang。与 brainstorm 的 expand–contract 同族，用在系统级演进。

## 架构特性与适应度函数

架构特性（性能、安全、一致性、可扩展性、可测性……）**互相冲突，全都要等于都没要**——每次架构决策都是特性优先级的显式取舍，必须说清"这次牺牲了什么、为什么值"。

**适应度函数**：把选定的架构特性编码成可客观执行的检查（测试、指标、门禁）——架构不再是文档里的愿望，而是 CI 里会红的检查。init 推荐的机械门禁（重复率 / 类型 / lint）就是它的最小形态：判断留给审查基准，exit code 守住已定的取舍。

## 分布式与韧性

跨进程 / 跨网络边界即适用（单进程内并发见范式工具箱）：

- **幂等是重试安全的前提**：任何可能被重试的操作（支付回调、消息消费、对账任务）先设计幂等键，再谈重试。
- **超时 + 重试退避 + 熔断**：慢依赖要有界（超时），瞬态失败可重试（指数退避 + 抖动），持续失败要快速失败（熔断不给下游陪葬）——三者配套出现，缺一是半套。
- **舱壁隔离**：每类依赖独立配额（连接池 / 并发额度），一个下游拖垮不了全局。
- **Outbox**：业务写入与事件发布要么同事务落库（先落 outbox 再投递），要么别承诺两者同时发生——双写必漂移。
- **Saga**：无两阶段提交的跨服务事务，靠补偿回滚。编排（中心协调）与协同（事件驱动）二选一，补偿逻辑才是真正的成本。
- **分布式谬误**一句话：网络不可靠、延迟非零、带宽有限、拓扑会变——跨边界设计按这个假设做。

## 范式工具箱

范式是工具箱不是阵营——同一系统多范式共存是常态，按问题域选工具：

- **函数式**：纯函数核心 + 脏边界（IO 推到边缘）；不可变优先；组合代替继承。并发与测试的友好度是买一送一。
- **并发**：消息传递优先于共享状态；单写者原则；能排队就别加锁。
- **声明式**：表驱动、schema 驱动、声明式 UI——数据比代码容易被机器校验，也容易被 AI 稳定生成。

## 反模式速查

投机泛化（为想象的未来加抽象）/ 隐藏默认值（`??` 兜底埋在 run 里，配置错误被吞成静默行为）/ 聪明代码（需要注释解释的技巧）/ 本地版分布式单体（一个包改，所有包跟着抖）。代码级坏味道以项目审查基准（Fowler 12 味，见 init 推荐骨架）为准，此处不重复。
