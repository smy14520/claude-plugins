在 tinder_develop 仓库协作时，用户的验收风格是证据驱动且范围极严：

1. **钢印证据**：交付必须附全量测试的完整运行输出与真实回环（ThreadingHTTPServer + port=0）E2E 实测记录，纯单元 Mock 或口头总结不算数；
2. **范围纪律**："超出即为违约"——明确裁剪的特性（热加载/延迟/CORS/body 模板化/查询匹配）绝不可顺手实现；
3. **主次分明**：mock-server 契约核心是静态精确匹配，`{name}` 路径参数只是顺手加分项，不得喧宾夺主；
4. **不轻信叙述**：验收消息可能描述与仓库史不符的状态（如"核心文件呈删除状态"），先 `git status`/`git show` 实证查证，如实报告差异，绝不附和无法证实的过程叙述。

**Why**: 用户在验收中明确说"别停在纯单元 Mock 上""给出交付总结与测试证据作为钢印"，且曾用不实的工作区描述测试我的查证习惯。

**How to apply**: 每次交付前跑全量测试并贴完整输出；任何"工作区异常"的说法先用 git 实证；功能取舍时对照已确认的范围清单。
