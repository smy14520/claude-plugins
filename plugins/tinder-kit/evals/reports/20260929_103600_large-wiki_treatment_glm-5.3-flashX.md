## 二、架构质量与模块设计 —— ★★★★★

### 2.1 接缝划分（Supervisor 核心关注点）

六 seam 单向依赖、前者不知后者，与 spec 宣称完全一致：

```
scan(34行) → parse(193行) → resolve(54行) → index(165行) → render(242行) → cli(205行, 薄层)
```

**深模块教科书式体现**：

- `resolve.py` 仅 54 行，却封装了"路径精确 → stem 精确 → 大小写兜底"全部解析策略，返回一个三态 `Resolution`——接口窄、实现深；
- `VaultIndex`（T8 重构）把 `by_name`/`by_path` 内部映射藏起来，cli 只调 `resolve_link()`，信息隐藏到位；
- `_emit()`（T5 重构）把五处 `--json` 分叉收拢为唯一收口，"输出模式分叉点只在 render 不在别处"的契约被结构强制而非注释许诺；
- **T6 单趟遍历是全场最佳**：`_traverse_links` 一趟 resolve 同时产出入向索引（backlinks 用）与死链/歧义发现（doctor 用），"同一事实两种视角不打架"由同源数据保证，还配了交叉一致性测试（`test_doctor_agrees_with_links_and_backlinks_on_same_facts`）钉死。

### 2.2 可指摘处（均不伤筋动骨）

1. **tags overview 排序落在 cli 层**（`_run_tags` 中 `key=lambda c: (-c.page_count, c.tag)`），而 `TagsOverviewResult` docstring 声称"条目已按 render 契约排序"——排序政策应下沉 render/index，注释与现实有一处轻微脱节；
2. **search 模块自行 scan+parse**（`search_vault` 不消费 `VaultIndex`）：好处是 search 短路避免了构建无关图索引的浪费，但 scan→parse 流水线接法在 `index.py` 与 `search.py` 出现两份，未来加缓存层时需改两处；
3. **`pages_for_tag` 潜伏边角**：父/子标签交错分布时（如 p1 有 `a/x`、p2 有 `a`、p3 有 `a/x`），字典插入序可能违反 docstring 声明的路径排序——现有 33 个固件未触发此布局，属极低概率潜伏项，建议后续补一条排序兜底（`sorted(pages.values(), key=path)`）。
4. 遗留 9 个 `worktree-agent-*` 分支未删——收尾卫生小疵。
