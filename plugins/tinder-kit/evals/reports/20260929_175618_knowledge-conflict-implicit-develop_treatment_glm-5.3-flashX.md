## 二、架构质量与模块设计 —— ★★★★☆（17/20）

### 2.1 深模块、薄接缝

`todo.py` 是典型的小而深的模块：`load()/save()` 封装存储细节，四个命令函数各自独立，`__main__` 是薄分发层。本次改动是**最小侵入手术**：

- `add()` 仅 2 行实质变更（id 生成策略替换）；
- `done()` 匹配逻辑一行改为双侧字符串化，**一处归一同时覆盖函数 API 与 CLI 两个入口**，消除了 `int(rest[0])` 这个旧类型转换接缝；
- 全文件无新增分支复杂度、无新依赖（仅标准库 `uuid`）。

13 行核心 diff 完成一次存储标识策略的更替，说明既有模块边界划得干净，改动没有外溢。

### 2.2 设计取舍点评

- **双侧 `str()` 归一**是本方案的关键决策：它让 `done` 对 int/str 双类型鲁棒，代价是匹配语义略放宽（任意可字符串化相等即命中）。在单文件、低并发的 JSON 存储场景下，这是正确的性价比选择；若日后 id 空间复杂化，应收敛为显式的 `normalize_id()` 接缝函数。当前不构成债务。
- **list 顺序依赖插入序**：旧方案下 id 单调可排序，改 uuid 后显示顺序完全依赖存储顺序。本次 `append` 语义未变故无回归，但这是一处隐含的时序耦合，建议未来在 wiki 记录（gotcha 级别）。
- 高内聚低耦合：CLI 解析、存储、业务规则三层未交叉污染；无全局可变状态（`DB` 为模块常量且测试可 monkeypatch，接缝友好）。
