## 0. 执行摘要

**一句话结论：这是一次"把错误的产品做对了"的交付——工程素养 A 级（分层、原子写、测试自纠、文档留痕均为范本级），但底牌中两次钉死的 `--priority <high|med|low>` 核心需求被静默丢弃，且该丢弃被 CONTEXT.md / spec.md 全文档链"合法化"固化，验收一票否决。**

- ✅ 硬禁令零违反：单 JSON 文件存储、零第三方运行时依赖、无 Web/GUI/多用户/同步，ADR 中对 SQLite 的否决与底牌逐字对齐；
- ✅ 架构与测试质量显著超出预期（temp+rename 原子写、`.bak` 轮转、`next_id` 高水位自纠均有测试背书）；
- ❌ **P0：优先级三档功能完全缺失**——`cli.add` 无 `--priority` 旗标、schema 无 priority 字段、list 无排序/展示，而督导在第 4 轮答复中明确重申"功能收敛在 add/list/done/delete **加 high/med/low 优先级**和多标签过滤"；
- ❌ 次级偏差：`list`→`ls`、`delete`→`rm` 改名无任何说明留痕；
- ⚠️ 在场督导第 5 轮"交付合格"的验收结论本身有盲区，本审计予以修正——返工清单极小（预计 ≤1 小时），复评预期 A-。

## 1. 需求兑现度与对齐质量 —— **6/10（含一票否决项）**

### 1.1 底牌逐项核对表

| 底牌条款 | 要求 | 交付实况 | 判定 |
| :--- | :--- | :--- | :--- |
| 存储介质 | 本地单一 JSON 文件 | `~/.todo/todo.json`，`TODO_HOME` 可覆盖；temp+rename 原子写 + `.bak` 轮转（超出要求） | ✅ 兑现+增益 |
| 绝对禁令 | 不引入任何数据库 | ADR-0001 明确否决 SQLite/todo.txt，"坚决不引入任何数据库"逐字对齐 | ✅ 严格兑现 |
| `add` 签名 | `add <title> [--tag] [--priority high\|med\|low]` | `add TITLE [--tag TAG]...`——**`--priority` 旗标不存在** | ❌ **P0 缺失** |
| 优先级支持 | high / med / low 三档 | 代码、schema、文档零提及；CONTEXT.md 反而写明"无 due / **priority** / notes" | ❌ **P0 缺失** |
| `list` | `list [--tag] [--all]` | 以 `ls` 实现，支持 `--tag`（可重复 AND/OR 组）与 `--all`，逻辑超配 | ⚠️ 功能兑现但改名无说明 |
| `done <id>` | 标记完成 | 幂等实现 + `completed_at` 时间戳 | ✅ 兑现+增益 |
| `delete <id>` | 删除任务 | 以 `rm` 实现，硬删 | ⚠️ 功能兑现但改名无说明 |
| 多标签 | 单/多标签 | `--tag` 可重复、逗号拆分、小写归一、去重排序 | ✅ 超额兑现 |
| Out-of-scope | 禁 Web/GUI/多用户/同步 | 全部未触碰；纯标准库零运行时依赖 | ✅ 严格兑现 |
| 边界增值 | —（未要求） | `reopen`、`tags`、`--json`（`--json` 经第 1 轮拍板批准） | ⚠️ reopen/tags 属未报备增值 |

### 1.2 P0 发现：priority 静默丢弃（五重证据链）

1. **底牌 §3 核心命令**：`add <title> [--tag <tag>] [--priority <high|med|low>]`，且 §3 独立条款"优先级支持：支持 high、med、low 三档"；
2. **第 4 轮督导答复**（全部访谈轮次之后、开工之前的最终范围重申）："功能收敛在 add/list/done/delete **加 high/med/low 优先级**和多标签过滤"；
3. **`src/tdo/cli.py`**：`add` 子解析器仅注册 `title` 与 `--tag`，无 `--priority`；
4. **`src/tdo/core.py`**：`add()` 构造的 task 字典为 `{id, title, tags, status, created_at, completed_at}`，无 priority 字段，`filter_tasks`/`tag_counts` 亦无优先级语义；
5. **`.forge/CONTEXT.md` / `.forge/v1/spec.md`**：前者明文"字段仅限：标题、标签、状态、创建/完成时间戳（无 due / **priority** / notes）"，后者领域规则字段清单同样无 priority——**说明这不是笔误，而是被决策文档系统性固化的错误范围**。

**根因推定**：第 3 轮 D1~D6 决策批量默认化时，"schema 字段范围（无 due/priority/notes）"被裹入"六项 D 全部按默认方案定案"的整批批准；第 4 轮督导重申范围与之冲突后，开发者未做 spec-reconcile，带着过时草案直接落盘实现。**责任双向**：开发者未对开工前最后一次范围重申做差异核对是主责；在场督导第 5 轮验收时未对照底牌逐项清点（只验收了存储边界），是本审计必须修正的流程盲区。

### 1.3 次级偏差

- `list`→`ls`、`delete`→`rm`：spec.md 仅解释了可执行名 `tdo`（因 `todo` 被本机占用），对子命令改名**只字未提、无理由留痕**。属低危，但违反"偏差须留痕"原则；
- `reopen`、`tags` 子命令为未报备增值（`--json` 已获第 1 轮批准，不算增值）。增值本身质量好，但未申报的 scope growth 应在交付清单中显式标注。

### 1.4 统一词汇表与决策留痕

- **CONTEXT.md（9/10）**：真正的 glossary 范本——Task/Tag/Pending/Done 四术语各带 `_Avoid_` 负面清单，Tag 的"无注册表、由 Task 派生、末引用消失即消亡"生命周期定义精准，AND/OR 过滤语义写死在词汇层。唯一硬伤：把 priority 排除写成了"本项目事实"，替错误决策背书；
- **ADR-0001（10/10）**：Considered Options（SQLite / todo.txt 双否决及理由）、Consequences（自认无并发锁、`.bak` 单代恢复窗口）、Revisit When 三段俱全，与底牌绝对禁令形成闭环证据；
- **spec.md（8/10）**：含一条极有价值的诚实注记——"`max + 1` 方案在删除最大 ID 任务后会复用 ID，**被测试实证推翻**，故增补 `next_id` 高水位"——这是测试驱动自纠的一手证据（`.pytest_cache/v/cache/lastfailed` 存在旁证开发期确有红灯）。扣分点：最终 spec 与最后一次批准范围（第 4 轮）不一致却标注"全部决议经用户逐项确认"。

## 2. 架构质量与模块设计 —— **9/10**

### 2.1 分层与深模块

```
cli.py（表现层：argparse / 打印 / 退出码 / store 装配）
   │ 依赖方向单向 ↓
core.py（纯领域：零 I/O，仅 datetime/typing 标准库导入）
store.py（持久化：原子性 / 版本校验 / 旧档迁移 全部隐藏）
```

- **深模块（Ousterhout 意义上）成立**：`store.load()` 以极小接口隐藏了"损坏检测 + 形状校验 + 版本拒识 + 旧档 next_id 重推"四重防御；`save()` 隐藏 temp+rename+`.bak` 轮转全套原子性机制。接口窄、实现深，是本次交付最大亮点；
- **接缝干净**：`core.filter_tasks` 返回 `(matched, unknown)` 二元组，把"未知标签检测"折叠进过滤接缝，由 cli 决定渲染为 stderr 提示——领域与呈现职责分离正确；
- **core 纯度**：全文件无 I/O、无全局状态，`done/reopen` 幂等且返回 `(task, changed)` 让上层决定是否写盘，避免无谓写放大；
- 退出码契约（0/1/2）在 cli 层集中定义，与访谈拍板一致。

### 2.2 扣分瑕疵（均不阻断）

1. **`save()` 崩溃窗口**：`os.replace(path, bak)` 与 `os.replace(tmp, path)` 之间若进程中断，主文件暂缺 → 下次 `load()` 落入"文件不存在→返回 empty()"分支，且下一次 save 会以空档覆盖 `.bak`，构成理论性全损路径。建议 load 增加主档缺失但 `.bak` 存在时的恢复分支；
2. **隐式变更协议**：`take_next_id(data)` 通过原地改写 `data["next_id"]` 生效，该副作用契约仅靠 docstring 约束"必须来自 store.load()"，cli→core 的协作依赖共享可变字典。当前规模可接受，若演进宜改为返回新 schema 的纯函数；
3. **无 fsync**：rename 前未刷盘，极端掉电可产生空/截断文件（有 `.bak` 兜底一线）。个人工具可接受，ADR 应自认此代价。

### 3.2 真实性核验（审计方法声明）

- 本审计沙箱未获解释器动态执行授权，采用**逐条静态推演**：19 项用例全部与实现对踪（含 `"[ ] 1 买牛奶 #shopping"` 行格式、`#3` 高水位、`already done` 幂等提示、`ghost` stderr 提示等具体断言逐字核对），**推演结论 19/19 通过**；
- 旁证：交付清单含三个测试模块的 `.pyc` 编译产物与 `.pytest_cache/v/cache/lastfailed`（证明 pytest 真实运行过且开发期存在红灯→修复循环，与 spec.md 的 next_id 自纠注记互证）、`dist/` 下 wheel+sdist 构建产物；
- 测试质量本身无 mock 自嗨、无同义反复断言，`tmp_path + monkeypatch` 隔离真实文件系统，是面向接缝的真测试。

### 3.3 缺口

- **priority 无从测试**——功能缺失的直接后果（根源计入维度 1，不重复扣）；

- endorsement.md 磁盘文件缺席：按单会话快车道 / Matt Pocock 直通模式规范，属标准行为，**不计缺陷**。

### 5.2 判定

- **验收判定：FAIL**（驳回返工）。依据：底牌 §3 将 priority 列入核心命令签名与独立功能条款，第 4 轮开工前重申仍然有效，交付物零实现且文档链固化排除——构成"隐性功能残缺"，触发一票否决；
- **综合评级：C**。工程面（架构/测试/留痕/交互）为 A 级水准，但向错误范围交付"完美实现"不构成合格交付；因缺失项单一、修复面小、无禁令违反，不降至 D。

### 5.3 返工清单（最小闭环，预估 ≤1 小时）

1. `cli.py`：`add` 增 `--priority {high,med,low}`（默认 med 或缺省，需在 spec 拍板）；
2. `core.py`：task schema 增 `priority` 字段；`ls` 展示优先级（行格式升级）并支持优先级排序或至少标注；
3. 测试：补 4 例——三档合法性（非法值 exit 2）、默认值、list 展示/过滤含 priority 的回归；
4. 文档：修订 `.forge/v1/spec.md` 领域规则与命令表、`.forge/CONTEXT.md` Task 词条（删除"无 priority"表述）、补一条 priority 语义 ADR；
5. 顺手项：spec 补记 `ls`/`rm` 改名缘由，交付清单显式申报 `reopen`/`tags` 增值。

### 5.4 复评预期与督导侧改进

- 返工后复评预期 **A-**：工程底座无需返工，priority 为纯增量；
- **督导侧整改**（本审计自我修正）：Turn 5 "交付合格"结论作废重开。今后验收前强制执行"底牌 diff 清单"（逐条核对核心命令签名），杜绝凭印象验收。
