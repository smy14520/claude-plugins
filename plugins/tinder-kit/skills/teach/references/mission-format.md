# MISSION.md 格式

`MISSION.md` 在工作区根目录。它承载用户学这个主题的 _原因_。每个教学决策（下一步教什么、呈现什么资源、设计什么练习）都应能追溯回这份文档。

## 模板

```md
# Mission: {Topic}

## Why
{1–3 句。用户追逐的具体现实目标：掌握这个技能后，他的生活或工作会发生什么变化？
避免"为了理解 X"这类抽象框定，逼出底层产出。}

## Success looks like
- {一件用户能做到的具体、可观察的事}
- {另一件具体的事}
- {…}

## Constraints
- {时间、预算、既有承诺、学习偏好——任何约束方法的因素}

## Out of scope
- {用户明确现在不想追的相邻主题，保护最近发展区}
```

## 规则

- **一个工作区一个 mission。** 用户想学两件不相关的事，就开两个工作区。
- **具体压倒抽象。** "十月前跑完半马"好过"变健康"；"给团队发一个 Rust CLI"好过"学 Rust"。
- **对含糊要推回。** 用户说不清为什么时，先访谈再动笔。坏的 mission 比没有更糟。
- **现实变了就修订。** mission 会变；目标移动时更新本文件，别留一个过时的 mission 牵着后续会话走。
- **保持短。** `MISSION.md` 超过一屏，它就不再是罗盘，而是计划。
