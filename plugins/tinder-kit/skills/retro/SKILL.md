用户请你做一次 **retrospective**。你在为项目的**环境**提议改进，让之后的会话走得更顺：把 agent 翻代码找不到的东西存下来，把会重复犯的错变成检查。

## Steps

1. 读这次会话的一手资料：主对话（含子 agent 的回报）；子 agent 的完整记录在本机会话日志里，量大时派 subagent 去读并只回报候选；以及 git log 与 `.forge/<slug>/` 下的产物。用户没指定会话时，默认当前会话。

2. 找候选。每条都要能指回会话里的某个具体时刻，指不回来的丢掉：
   - **踩坑（Gotcha）**：反直觉的平台或依赖行为。附可在终端跑通的复现命令与真实输出，复现不出来的不提。
   - **隐性联动（Cross-cut）**：改 A 必须联动 B 的链路、仓库外的消费者——代码里 grep 不到的。
   - **过时记录**：会话里出现的新决定或新事实，与已有的 CONTEXT、ADR、wiki 条目或规则矛盾。
   - **可机械化的错误**：agent 犯的、lint / 类型 / 测试 / hook 能拦住的错，提议检查而不是一句规则。
   - **导航**：agent 花了很久才找到某个文件或事实，就在它本来会读的文件里加指针。

3. 按严重程度把候选列给用户，每条写明：来自会话的哪一刻、放到哪一层、草稿内容。由用户选定哪些、怎么改。

4. 只写用户选中的，按下方的归位与格式写入。ADR 与术语按 `domain-modeling` 的格式写。

## 归位：三问

依次问，第一个答"是"的就是归宿：

1. **是全项目任何任务都必须遵守的底线吗？** → `CLAUDE.md`。例：“包管理器统一用 pnpm”。某个图表库的配置写法不算。
2. **模型在这里有默认犯错的倾向，且能写成一句简短的正向准则吗？** → `.claude/rules/<domain>.md`。例：“数据库查询走原生 SQL，不引入 ORM”。支撑这条结论的 benchmark 报告进 wiki，结论进 rules。
3. **是长尾、平时用不上、碰到了就要命的隐性事实吗？** → `.forge/wiki/<type>/`：
   - `gotcha/`：反直觉的平台 Bug、依赖库怪癖、版本兼容问题，必须附复现；
   - `cross_cut/`：多文件或跨仓库的修改链路；
   - `decision/`：ADR；
   - `concept/`：复杂业务实体与机制的展开。

三问都是“否”——通常是代码能自证的事实——就不写。

## 写入格式

1. 读 `.forge/wiki/tags.md`，选 2~4 个既有标签；确有新领域时按该文件头部的规则登记新标签。
2. 写 `.forge/wiki/<type>/<slug>.md`，frontmatter 含 `title`、`type`、`tags`、`description`，可选 `anchors`（相关代码符号）。
3. 在 `.forge/wiki/index.md` 对应分类下追加一行：`- [{title}]({type}/{slug}.md) — {description} [{tag1}, {tag2}]`。
4. 改写过时记录时原地改成现状，并附一行说明原先是什么、为什么变了。
